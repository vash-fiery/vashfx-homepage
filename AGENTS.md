# AGENTS.md

## Scope

These instructions apply to the entire repository. If a more specific
`AGENTS.md` exists in a subdirectory, follow that file for work in its scope.

## Repository snapshot

- This is a React 19 single-page application written in TypeScript 6 and built
  with Vite 8. npm 11.19.0 is pinned through `packageManager`.
- `@cloudflare/vite-plugin` runs the Worker in the Workers runtime during local
  development and builds the frontend and Worker together.
- Browser code lives in `src/`; imported assets live in `src/assets/`; files
  requiring stable root-relative URLs live in `public/`.
- `worker/index.ts` is the module Worker entry point and handles application
  API requests under `/api/`.
- `wrangler.jsonc` configures the Worker, SPA fallback, bindings,
  compatibility settings, observability, and source-map uploads.
- The deployable configuration binds static assets as `ASSETS`, the R2 bucket
  `vfx` as `BUCKET`, and the Analytics Engine dataset `ds_events` as `DS`.
  `account_id` is not committed.
- `assets.run_worker_first` is omitted, so matching static assets are served
  before the Worker. With the current SPA fallback and compatibility date,
  unmatched browser navigation requests are served `index.html` without
  invoking the Worker; unmatched non-navigation requests can reach it.
- `worker/index.ts` currently returns the same JSON response for every method
  and path under `/api/*`, then returns `404` for other requests that reach the
  Worker. A matching static file can take precedence over a Worker route.
- Application code currently uses none of the configured bindings. The
  checked-in generated `Env` contains `ASSETS` and `BUCKET`, but not `DS`; do
  not use `DS` until `npm run cf-typegen` has synchronized the generated file.
- `worker-configuration.d.ts` is generated by Wrangler. Do not edit it by hand.
- `.github/workflows/node.js.yml` builds and lints with Node.js 24 and 26. Its
  active deploy job runs `npm run deploy` with `CLOUDFLARE_API_TOKEN` after a
  successful build for pushes to `main` and manual `workflow_dispatch` runs;
  it is skipped for pull requests.
- A push to `main` can therefore deploy production through GitHub Actions.
  Cloudflare Workers Builds may be a second deployment path if it remains
  enabled in the Cloudflare dashboard; repository files cannot prove its live
  settings, so confirm deployment ownership before changing either system.
- `.github/workflows/codeql.yml` analyzes GitHub Actions and
  JavaScript/TypeScript changes.
- `.github/dependabot.yml` checks npm and GitHub Actions dependencies daily and
  assigns its update pull requests to `vash-fiery`.
- `.github/workflows/labeler.yml` runs on `pull_request_target` and reads
  `.github/labeler.yml`. Treat this as a privileged workflow: it must not check
  out a pull request head or execute pull-request-controlled code.
- `@openai/codex` 0.147.0 is declared as a project dependency. No npm script
  invokes it, application code does not import it, and the repository does not
  currently contain an OpenAI API or Agents SDK integration.
- No `SECURITY.md` is currently committed. Its absence does not establish an
  accepted risk, exclusion, or authorization decision.

## General change rules

- Read complete relevant files, not only search snippets or diffs.
- Keep changes narrowly scoped and preserve unrelated user work.
- Use TypeScript and ES modules. Prefer explicit, narrow types and avoid
  `any`, unsafe double-casts, and unexplained TypeScript suppressions.
- Treat Oxlint as a linter, not a formatter. Existing files contain mixed
  legacy quote, semicolon, and indentation styles; do not normalize unrelated
  lines during a scoped change.
- For new or substantially rewritten TypeScript and TSX, use two-space
  indentation, single quotes, no semicolons, and an approximately 80-column
  target. For surgical edits, preserve the surrounding file's style.
- Never commit credentials, API tokens, production secrets, or local
  environment values.
- Keep developer tooling separate from browser and Worker runtime code. The
  presence of `@openai/codex` does not authorize an OpenAI API integration or
  make Codex a runtime dependency.
- Do not silently change public routes, binding names, compatibility behavior,
  CI deployment triggers, or production resources.

## Frontend rules

- Put browser UI and client behavior in `src/`.
- Use React function components and hooks. Keep state minimal and avoid
  duplicated sources of truth.
- Prefer existing stylesheets and custom properties over inline styles.
- Preserve responsive behavior, light/dark color support, semantic HTML,
  keyboard access, visible focus, useful labels, and meaningful alternative
  text.
- Keep client requests aligned with the Worker route and response contract.

## Worker rules

- Put Worker request handling in `worker/`. Treat `/api/*`, static-asset
  routing, SPA navigation fallback, and the Worker's `404` fallback as
  separate public contracts; do not move behavior between them implicitly.
- Use module Worker syntax and validate handlers with
  `satisfies ExportedHandler<Env>`.
- Keep request-scoped state inside handlers or function arguments. Do not put
  mutable request data or binding-derived clients in module-level state.
- Handle every Promise by awaiting it, returning it, intentionally discarding
  it with `void`, or passing it to `ctx.waitUntil()`.
- Use `ctx.waitUntil()` for work that may continue after the response. Do not
  destructure `waitUntil` from `ctx`.
- Stream large or unknown-size request and response bodies. Buffer only data
  whose size is known and bounded.
- Use KV, R2, Analytics Engine, and service bindings directly through `env`;
  do not call the Cloudflare REST API from the Worker for bound resources.
- With `assets.run_worker_first` omitted, matching assets take precedence over
  Worker code, and unmatched SPA navigation requests take the asset fallback.
  Account for static-file shadowing and navigation semantics when changing an
  API route. Use a verified `run_worker_first` route pattern only as an
  explicit routing change.
- The current `/api/*` handler matches every HTTP method and every path with
  that prefix. Preserve that breadth only when intentional; new handlers
  should match paths and methods explicitly and return `404` or `405` as
  appropriate.
- If adding R2 behavior, treat keys, methods, headers, ranges, preconditions,
  request bodies, and stored metadata as untrusted. Validate and authorize
  each operation, bound uploads, and return `405` with an `Allow` header for
  unsupported object methods. The configured `BUCKET` binding alone does not
  make the bucket publicly reachable.
- Analytics Engine `writeDataPoint()` is non-blocking and is not awaited.
  Keep its ordered field schema stable, use only one index, and do not record
  secrets or unnecessary personal data.
- Await service-binding calls. A dropped service-binding Promise can terminate
  before the target finishes.
- Return explicit status codes and stable JSON shapes. Log internal details
  with structured `console.error` data, but expose only safe error messages to
  clients.
- Use Web Crypto for security-sensitive randomness and comparisons. Never use
  `Math.random()` for tokens or identifiers that must be unpredictable.

## Wrangler, bindings, and secrets

- Treat `wrangler.jsonc` as the source of truth for deployable Worker
  configuration. Verify fields against the installed Wrangler schema.
- The current configuration declares `ASSETS`, R2 `BUCKET`, and Analytics
  Engine `DS`, but application code currently uses none of them. Confirm the
  live file and generated `Env` before using any binding; `DS` is not yet
  present in the checked-in generated type file.
- Binding names are exact and case-sensitive. A rename requires matching code,
  generated types, local validation, and an infrastructure migration plan.
- After any binding, secret declaration, compatibility, environment, or module
  rule change, run `npm run cf-typegen`, review the generated diff, and then run
  `npx wrangler types --check`.
- If `npx wrangler types --check` fails, regenerate the file; never patch the
  generated `Env` interface manually.
- Review the compatibility-flags documentation before changing
  `compatibility_date` or `compatibility_flags`, then test the affected Worker
  behavior. Do not bump the date as an unrelated cleanup.
- Keep `nodejs_compat` unless a tested task explicitly removes the need for it.
- Keep observability enabled. Choose log or trace sampling rates deliberately
  when traffic volume or cost requires it, and prefer structured logs.
- `account_id` is optional and intentionally omitted. Do not add it as an
  unrelated fix. For deployment account errors, first inspect the failing
  GitHub Actions or Workers Builds log and its environment; set
  `CLOUDFLARE_ACCOUNT_ID` in that deployment system only when the verified
  account selection requires it.
- Use either `.dev.vars` or `.env` for local secrets, not both. Both patterns
  are ignored except for tracked example files.
- Use Wrangler secrets for deployed sensitive values. Remember that
  `wrangler secret put` and `wrangler secret delete` create and deploy a new
  Worker version, so they require explicit authorization.
- Local bindings are simulated by default. Never opt into remote resources or
  mutate production data merely to validate a change.

## Dependencies and CI

- Change dependencies with npm so `package.json` and `package-lock.json` stay
  synchronized. Do not hand-edit lockfile resolutions or integrity hashes.
- Review release notes, engine requirements, peer dependencies, and lockfile
  churn for upgrades.
- Before approving a dependency lifecycle script, run
  `npm approve-scripts --allow-scripts-pending`, inspect the exact installed
  package and version, and approve or deny only explicitly reviewed packages.
  Do not use `npm approve-scripts --all` without explicit authorization.
- Dependabot opens separate daily npm and GitHub Actions update pull requests.
  Review the exact bot diff, release notes, lockfile or action-reference
  changes, and all relevant checks; do not treat an automated update as
  pre-approved.
- Read complete workflow files before editing events, matrices, permissions,
  secrets, or conditions.
- `pull_request_target` runs with base-repository context and can have write
  permissions. Never use it to check out an untrusted pull request head, run
  pull-request-controlled scripts, or consume untrusted artifacts.
- GitHub label names are case-sensitive. Preserve existing names unless the
  task explicitly includes a coordinated label migration.
- GitHub Actions currently owns an active Wrangler deployment job. Do not
  change its events, `if` condition, environment, token source, permissions,
  or deployment command without explicit deployment authorization.
- Distinguish GitHub Actions jobs from external checks such as Workers Builds.
  A green Actions run does not prove the external deployment succeeded.
- Keep the GitHub deployment credential in the
  `CLOUDFLARE_API_TOKEN` Actions secret. If Workers Builds is also enabled,
  keep its separate user token in Cloudflare Settings > Build; never copy or
  print either credential.
- Treat a direct push to `main`, a manual run of the Cloudflare Worker
  workflow, and changes to either deployment system as deployment-sensitive
  actions. A pull-request run builds and lints but skips the deploy job.

## Security review boundaries

- Resolve applicable `SECURITY.md` files before a security scan. There is no
  policy today, so do not invent exclusions, accepted risks, or severity
  downgrades; ask the owner when a decision would affect reportability.
- Treat the public Worker request, URL, method, headers, body, and
  pull-request-controlled content as attacker-controlled. Treat data from a
  bound resource as untrusted when code begins reading it.
- Trace candidate findings from an attacker-controlled source to a meaningful
  sink and verify reachability against `wrangler.jsonc`, route ordering,
  bindings, and deployment triggers before assigning severity.
- Do not report the configured but unused `BUCKET` or `DS` binding as a public
  data path without source evidence that makes it reachable.
- CodeQL, dependency alerts, and Codex Security findings are evidence, not
  proof. Validate them in source and do not dismiss or suppress them solely
  because another scanner is green.
- A review or scan does not authorize a fix, secret access, disclosure,
  deployment, alert dismissal, issue creation, or accepted-risk decision.
- Keep exploit detail proportionate and never put live secrets, sensitive R2
  data, or unnecessary reproduction payloads in repository guidance, issues,
  pull requests, or logs.

## Repository guidance maintenance

- Update `AGENTS.md` and `SKILLS.md` together when a rule and its repeatable
  playbook change as one unit.
- Re-read the current tree, package scripts, Wrangler configuration, and
  relevant automation before changing repository snapshots. Do not carry
  forward versions, bindings, branches, or check results from an earlier
  conversation.
- Keep stable requirements separate from current-state observations. Verify
  every command, path, workflow name, trigger, and external link included in
  the documentation.
- Remove or consolidate conflicting guidance instead of appending another
  exception. Add a skill only for a repeatable workflow that is materially
  distinct from an existing playbook.
- Keep this root `AGENTS.md` concise enough to load for every task. Put
  procedures in `SKILLS.md` or, when automatic Codex skill discovery is
  required, in `.agents/skills/<skill-name>/SKILL.md`.
- `SKILLS.md` is a repository-maintained playbook index; Codex does not load it
  as a folder-based skill merely because of its filename. Do not claim a skill
  is installed until its `SKILL.md` exists in a supported skill directory.

## Validation

Use the smallest relevant validation set and report exactly what ran.

| Change type | Required validation |
| --- | --- |
| Documentation only | Review Markdown, commands, paths, links, and `git diff --check` |
| Frontend or styling | `npm run lint`, `npm run build`, and focused local UI checks |
| Worker behavior | `npm run lint`, `npm run build`, local route checks, and `npx wrangler deploy --dry-run` |
| Wrangler or bindings | `npm run cf-typegen`, `npx wrangler types --check`, `npm run build`, and `npx wrangler deploy --dry-run` |
| Dependency changes | `npm ci`, install-script review, `npm run lint`, and `npm run build` |
| GitHub workflow | YAML review plus the same local commands used by the workflow |
| GitHub automation | Review triggers, permissions, untrusted-input boundaries, configuration syntax, and affected label or update behavior |
| Security review or fix | Applicable policy chain, source-to-sink validation, focused reproduction, then the validation required by the changed code |
| OpenAI integration | Official API or Agents SDK docs, server-side secret handling, lint, build, and focused mocked or authorized API-path checks |

For route changes, exercise the successful path and at least one relevant
failure path. Check both the SPA and affected `/api/` routes when a change
crosses the frontend/Worker boundary.

There is currently no automated test script. Do not describe lint, build,
type-generation checks, dry runs, or manual checks as automated tests.

## Commits, pull requests, and deployment

- Do not modify or stage unrelated files.
- Confirm a pull request is open and its head is current before updating it.
  Do not reopen a closed pull request or continue its stale branch without
  explicit authorization; base replacement work on the current default branch.
- Prefer an `agent/<description>` branch and a pull request. A direct push to
  `main` triggers the GitHub Actions deploy job and can deploy production.
- A pull request to `main` triggers lint and build jobs but skips the GitHub
  deploy job. If Cloudflare Workers Builds is enabled externally, a branch may
  also create a preview; verify its dashboard configuration instead of
  assuming that behavior.
- Use concise commit subjects that describe completed changes.
- Pull requests must summarize impact, Cloudflare or deployment risk, and the
  validation commands actually run.
